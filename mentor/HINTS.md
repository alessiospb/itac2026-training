# Подсказки наставника — спойлеры

Открывайте по одной группе после самостоятельного исследования.

## Диагностика

- Сравните первый запуск и retry. Все ли зелёные тесты действительно проверяют поведение?
- Запустите каждый тест отдельно. Затем попробуйте несколько workers.
- Изучите beforeAll, состояние страницы и localStorage.

## Что заложено в исходный проект

- Фиксированные паузы короче возможных задержек приложения.
- Мгновенные проверки count/textContent/isVisible вместо повторяемых assertions.
- Общая страница и browser context, зависимость сценариев от порядка и чужой корзины.
- Checkout не создаёт собственные предусловия; поиск зависит от загрузки каталога.
- Исключения в негативном тесте поглощаются, создавая ложный passed.
- Пропущенный тест купона и слабое покрытие негативных сценариев.
- any в Page Object, ослабленный TypeScript и хрупкие позиционные локаторы.
- Retries маскируют нестабильность; CI продолжает работу после неудачного тестового шага.
- Нет traces, доказательств серии запусков и публикации отчёта.

## Направление решения

Используйте встроенный page fixture для изоляции. Ищите элементы по role/label и ограничивайте поиск карточкой товара. Ждите наблюдаемого результата каждого действия. API допустим для подготовки там, где это обосновано, но пользовательский сценарий должен проверяться через UI. Включите полезные traces и строгую типизацию. Не стройте универсальный framework ради небольшого набора тестов.

Пять запусков считайте по exit code и итоговой статистике: retries=0, failed=0, flaky=0, ожидаемое число тестов и отсутствие необъяснённых skipped. Сохраняйте отдельные отчёты, поскольку следующий запуск перезаписывает стандартный каталог.

Готовое решение специально не включено: его можно сделать после тренировки и сравнить с вашим.
